Project Overview

SAT-1 is a space-themed embedded system developed on the ESP32-S3 using FreeRTOS. A pushbutton connected to GPIO18 simulates a ground command sent to a satellite. Pressing the button generates a hardware interrupt that activates a minimal Interrupt Service Routine.

The ISR signals two bottom-half tasks using a Binary Semaphore and a Direct Task Notification. Their wake-up latency is measured under idle and loaded processor conditions using the Wokwi Logic Analyzer.

Application 5 runs as the system spine. Its interrupt-driven command path is the backbone of SAT-1, extended with the interrupt and synchronization work from Application 3 and the periodic background tasks from Application 2. Those background tasks create processor load during interrupt testing, so the integrated system demonstrates interrupt handling, task synchronization, scheduling, timing analysis, and engineering documentation in one coherent product.

System Architecture

System Flow

The ISR responds immediately to the GPIO18 falling edge and performs only ISR-safe operations. It records a timestamp, applies debounce protection, generates a GPIO19 timing pulse, and signals both bottom-half tasks.

Longer processing and reporting are deferred to FreeRTOS task context. The Binary Semaphore and Direct Task Notification paths are measured separately so their wake-up behavior can be compared.

Tasks and Timing Evidence

Task Table and WCET Evidence

To obtain accurate worst-case execution time (WCET) measurements for the background load tasks, the original Application 3 scaffold was instrumented with a boot-time self-test. Before the periodic tasks begin executing, each load task runs multiple times in isolation on Core 1 without interference from other tasks. This allows the measured execution times to represent the task's actual computation time rather than a response time inflated by preemption. These measured WCET values were then used to compute processor utilization as Ui = Ci / Ti.

Schedulability

The four periodic load tasks use fixed-priority preemptive scheduling with priorities assigned according to the Rate-Monotonic policy, where shorter periods receive higher priorities. Each task's deadline is equal to its period. For four independent periodic tasks, the Rate-Monotonic sufficient utilization bound is:

URM = 4(21/4 − 1) ≈ 0.7568

The measured processor utilization for the periodic task set is U = 0.3623. Since 0.3623 < 0.7568, the task set satisfies the Rate-Monotonic schedulability test. Because the utilization is also below the EDF feasibility limit of 1.0, the task set is schedulable under both Rate-Monotonic and Earliest Deadline First scheduling.

The Binary Semaphore and Direct Notification bottom-half tasks are event-driven rather than periodic, so they are not included in the utilization calculation. Their real-time performance is evaluated instead using the measured wake-up latency following an interrupt.

Hazard Analysis

Hazards are mapped to IEC 61508, the functional-safety standard for electrical, electronic, and programmable electronic safety-related systems, and to MISRA C:2012 for coding-level requirements.

Hazard Effect Mitigation Standard mapping
Long ISR execution Increased interrupt latency Keep the ISR minimal and defer processing to bottom-half tasks IEC 61508-3 — software architectural design and real-time behavior
Button bounce Repeated interrupt events Apply timestamp-based debounce logic IEC 61508-7 — techniques and measures (input filtering and signal conditioning)
Missing scheduler yield Delayed bottom-half execution Use portYIELD_FROM_ISR() when a higher-priority task is awakened IEC 61508-3 — software design and task synchronization
Heavy processor load Increased bottom-half latency Use fixed-priority scheduling and verify timing IEC 61508-3 — timing analysis and deterministic scheduling
Non-ISR-safe function call Unpredictable behavior or system failure Use only ISR-safe FreeRTOS APIs inside the ISR MISRA C:2012 Directive 4.1 — run-time failure avoidance

Fault Injection and Graceful Degradation

Fault Introduced

The scheduler-yield call was temporarily removed from the ISR: 

// portYIELD_FROM_ISR(higher_woken);

Prediction

The ISR should continue delivering both signals, but the awakened bottom-half tasks might not run immediately after the ISR returns. Their response was expected to become slower and less deterministic.

Observation

Interrupts continued to be detected, and both bottom-half tasks still executed. However, their wake-up timing became less immediate and less predictable.

Recovery

The line was restored in the final working implementation: 

portYIELD_FROM_ISR(higher_woken);

The system therefore degraded in timing performance rather than failing completely. Interrupt detection and event delivery remained operational throughout the experiment.

Final Reflection

What I Would Do Differently

If I were starting this project again, I would spend more time planning the task priorities and system architecture before writing code. As the project grew, it became more difficult to keep track of how the interrupt service routine, bottom-half tasks, and periodic background tasks interacted with one another. I also would have organized the project documentation and GitHub Pages site earlier instead of waiting until the end of the semester. Having the documentation completed as the project progressed would have made the final integration much easier and reduced the amount of work required during the last week.

What Was Harder Than Expected

The most difficult part of the project was measuring and understanding timing behavior. It was one thing to write FreeRTOS tasks that worked correctly, but it was another to verify interrupt response time and explain why latency changed when background tasks were running. Using the Wokwi Logic Analyzer and comparing the Binary Semaphore and Direct Task Notification paths helped me better understand how scheduling decisions affect system performance. Integrating work from multiple applications into one final project also required more effort than I originally expected because each application had been developed independently throughout the semester.

The Most Valuable Thing I Learned

The most valuable lesson I learned was to keep interrupt service routines as short as possible and defer additional processing to a bottom-half task. Before this course, I knew interrupts were important, but I did not fully understand why embedded systems separate time-critical work from normal task execution. Seeing the difference in measured interrupt latency and task wake-up time made the concept much more meaningful. This project also gave me more experience with FreeRTOS, task scheduling, timing analysis, and documenting engineering decisions, all of which are skills I can discuss during interviews and apply in future embedded systems projects.
